1. ¿Qué hace @Entity? ¿Por qué se requiere el constructor vacío?
--------------------------------------------------------------------------------
Respuesta:
a) Rol y función de @Entity:
   - La anotación @Entity (del paquete jakarta.persistence o javax.persistence) es la marca fundamental del estándar JPA (Java Persistence API). Le indica al motor de persistencia (en nuestro caso, Hibernate) que la clase Java en cuestión es una Entidad de Dominio que debe mapearse bidireccionalmente a una tabla de base de datos relacional.
   - Gracias a @Entity:
     1. Mapeo Objeto-Relacional (ORM): Hibernate interpreta cada atributo de la clase como una columna de la tabla (por defecto, la tabla recibe el nombre de la clase, 'contacto', y las propiedades 'nombre', 'apellido', 'email', 'telefono' se convierten en columnas de tipo VARCHAR).
     2. Ciclo de vida y gestión de persistencia: Las instancias de la clase pasan a ser gestionadas por el EntityManager (contexto de persistencia), permitiendo que Hibernate detecte automáticamente modificaciones en los objetos (dirty checking), ejecute consultas y mantenga la coherencia transaccional sin requerir sentencias SQL manuales.
     3. Creación automática del esquema (DDL): Al iniciar la aplicación con 'spring.jpa.hibernate.ddl-auto=update', Hibernate inspecciona las clases anotadas con @Entity y genera de forma automática la instrucción DDL 'CREATE TABLE IF NOT EXISTS contacto (id BIGINT GENERATED BY DEFAULT AS IDENTITY, nombre VARCHAR(255), ... PRIMARY KEY (id))'.

b) ¿Por qué se requiere obligatoriamente el constructor vacío (no-argument constructor)?
   - El estándar JPA exige que toda entidad cuente con un constructor sin argumentos (public o protected) debido al mecanismo de Reflexión de Java (Java Reflection API) que utiliza el proveedor de persistencia (Hibernate):
     1. Reconstrucción de objetos desde la base de datos: Cuando se ejecuta una consulta como 'repo.findAll()' o 'repo.findById(1L)', Hibernate recupera las filas de la tabla de la base de datos (tuplas relacionales). Para convertir esas filas en instancias de objetos Java en memoria, Hibernate primero instancia la clase utilizando reflexión mediante `Contacto.class.getDeclaredConstructor().newInstance()`, el cual invoca exclusivamente el constructor vacío.
     2. Poblamiento de atributos: Una vez creado el objeto vacío en memoria, Hibernate utiliza los métodos de acceso setters o accede directamente a los campos privados (Field Access) para depositar los valores leídos de las columnas de la BD.
     3. Generación de proxies dinámicos y Lazy Loading: Hibernate crea clases proxy en tiempo de ejecución (subclases sintéticas) para gestionar la carga diferida y la interceptación de métodos; estas subclases requieren invocar 'super()' sin argumentos.
   - Si no existiera el constructor vacío (por ejemplo, si solo definiéramos el constructor con parámetros), el compilador Java removería el constructor predeterminado por omisión y Hibernate arrojaría una excepción fatal al iniciar o consultar: `org.hibernate.InstantiationException: No default constructor for entity: com.gremio.model.Contacto`.


2. ¿Por qué ContactoRepository no tiene ningún método escrito pero aun así puedes llamar findAll() y save()?
--------------------------------------------------------------------------------
Respuesta:
Esta capacidad es la principal innovación y fortaleza del módulo Spring Data JPA:

a) Jerarquía de Interfaces de Spring Data:
   - Nuestra interfaz se define como: `public interface ContactoRepository extends JpaRepository<Contacto, Long>`.
   - Al heredar de JpaRepository, ContactoRepository hereda implícitamente una rica cadena de interfaces padre:
     * `Repository<T, ID>`: Marcador base del patrón Repository de Domain-Driven Design (DDD).
     * `CrudRepository<T, ID>`: Declara las operaciones fundamentales de persistencia (save, saveAll, findById, existsById, findAll, findAllById, count, deleteById, delete, deleteAll).
     * `PagingAndSortingRepository<T, ID>`: Añade soporte para paginación y ordenamiento automático.
     * `ListCrudRepository<T, ID>` y `JpaRepository<T, ID>`: Especializaciones de JPA que refinan los tipos de retorno a List<T>, añaden operaciones por lotes (flush, saveAndFlush, deleteInBatch).

b) Generación dinámica de Proxy en tiempo de ejecución (Dynamic Proxies):
   - ContactoRepository es solo una interfaz (contrato), no una clase concreta, por lo que no contiene código ejecutable escrito por nosotros.
   - Al arrancar la aplicación, el motor de Spring Data escanea los paquetes en busca de interfaces que extiendan JpaRepository.
   - Para cada repositorio encontrado, Spring genera dinámicamente un objeto Proxy en memoria (utilizando proxies dinámicos de JDK o bytecode con CGLIB) y le delega la ejecución a una clase de implementación genérica prefabricada provista por Spring: `SimpleJpaRepository<T, ID>`.
   - Cuando en nuestro ContactoController invocamos `repo.findAll()`, en realidad se ejecuta el método `findAll()` de `SimpleJpaRepository`, el cual interactúa internamente con el `EntityManager` de JPA ejecutando una consulta JPQL: `SELECT e FROM Contacto e` y traduciéndola al SQL nativo de H2: `SELECT * FROM contacto`.

c) Parámetros Genéricos <Contacto, Long>:
   - Al especificar `<Contacto, Long>`, le comunicamos a Spring el tipo de Entidad que administrará y el tipo de dato de su Clave Primaria (@Id). Esto permite que todos los métodos hereden un tipado fuerte sin necesidad de casteos (por ejemplo, `findById(Long id)` retorna `Optional<Contacto>`, y `findAll()` retorna `List<Contacto>`).


3. ¿Qué diferencia hay entre @GetMapping y @PostMapping? ¿Cuándo usarías cada uno?
--------------------------------------------------------------------------------
Respuesta:
Ambas anotaciones son especializaciones de `@RequestMapping` en Spring MVC y se mapean directamente a los verbos semánticos fundamentales del protocolo HTTP:

a) @GetMapping (Método HTTP GET):
   - Propósito y Semántica: Se utiliza para SOLICITAR y RECUPERAR información del servidor sin modificar el estado del sistema.
   - Características:
     * Seguro (Safe) e Idempotente: Realizar la petición múltiples veces produce el mismo efecto y no genera efectos secundarios destructivos en los datos del servidor.
     * Visibilidad: Los parámetros enviados viajan visibles en la URL (como Query Parameters: `/contactos?pagina=1` o Path Variables: `/editar/5`).
     * Navegabilidad y Caché: Las URLs GET pueden ser cacheadas por navegadores y proxies, guardadas en favoritos (bookmarks) y compartidas por enlaces.
   - En nuestro laboratorio:
     * `@GetMapping("/contactos")`: Para consultar y renderizar la lista completa de contactos.
     * `@GetMapping("/nuevo")`: Para solicitar y mostrar la página HTML con el formulario vacío de captura.
     * `@GetMapping("/editar/{id}")`: Para solicitar y precargar el formulario con los datos del contacto específico.

b) @PostMapping (Método HTTP POST):
   - Propósito y Semántica: Se utiliza para ENVIAR datos hacia el servidor con el fin de PROCESAR, CREAR o MODIFICAR recursos en el sistema.
   - Características:
     * No Idempotente y No Seguro: Enviar la misma petición dos veces puede provocar la inserción duplicada de un registro. Por ello los navegadores muestran la advertencia "¿Desea reenviar el formulario?" si el usuario recarga la página.
     * Cuerpo de la petición (Request Body): La información viaja encapsulada dentro del cuerpo HTTP (payload), generalmente codificada como `application/x-www-form-urlencoded` o `application/json`. No queda visible en la barra de direcciones del navegador ni en los historiales web, lo que brinda confidencialidad para contraseñas o datos personales.
     * Sin límite de longitud estricto: A diferencia de la URL de un GET (limitada usualmente a 2048 caracteres), POST puede transportar grandes volúmenes de datos o archivos adjuntos.
   - En nuestro laboratorio:
     * `@PostMapping("/guardar")`: Para recibir los campos del formulario (`@ModelAttribute Contacto contacto`) y persistirlos en la base de datos H2 mediante `repo.save(contacto)`.

c) Regla de decisión para saber cuándo usar cada uno:
   - Usa @GetMapping cuando el usuario esté consultando, leyendo, filtrando o buscando datos, o solicitando la visualización de una pantalla/formulario (lectura pura).
   - Usa @PostMapping cuando la acción del usuario altere el estado del servidor (crear una cuenta, guardar un contacto, realizar una compra, autenticarse con usuario y contraseña).


4. Módulos de Update y Delete: ¿Cómo gestiona Spring Data JPA la actualización y eliminación?
--------------------------------------------------------------------------------
Respuesta técnica adicional sobre la implementación de Update y Delete:

a) Actualización (Update):
   - En Spring Data JPA no existe un método separado llamado `update()`. El método `save()` cumple una función dual inteligente (Upsert):
     * Si `contacto.getId() == null`: Hibernate detecta que la entidad es transitoria (nueva) y ejecuta una instrucción SQL `INSERT INTO contacto ...`.
     * Si `contacto.getId() != null`: Hibernate detecta que la entidad ya posee una clave primaria y ejecuta una instrucción SQL `UPDATE contacto SET nombre=?, apellido=?, email=?, telefono=? WHERE id=?`.
   - Por esta razón, en nuestra plantilla `editar.html` incluimos el campo oculto `<input type="hidden" th:field="*{id}" />`. Al someter el formulario a `/guardar`, el objeto Contacto reconstruido por Spring MVC preserva su ID original, permitiendo que `repo.save(contacto)` actualice el registro existente en lugar de duplicarlo.

b) Eliminación (Delete):
   - Implementado mediante el endpoint `@GetMapping("/eliminar/{id}")` (y opcionalmente `@PostMapping("/eliminar/{id}")`).
   - El controlador recibe el `@PathVariable("id") Long id` y ejecuta `repo.deleteById(id)`.
   - Spring Data JPA verifica la existencia del registro y ejecuta la instrucción SQL `DELETE FROM contacto WHERE id = ?`.
   - Finalmente, el controlador retorna `"redirect:/contactos"` (patrón Post/Redirect/Get) para refrescar la vista de la tabla mostrando la lista actualizada de forma inmediata.
